# Clean Architecture Refactoring Plan for GraphQL Gateway

## Overview
This refactoring will transform the gateway from a simple GraphQL-to-gRPC proxy into a properly layered clean architecture application.

## Current State
- Resolvers directly call gRPC clients (some cases)
- Partial service layer exists (only for transactions)
- No domain layer
- No use cases layer
- Business logic mixed in resolvers

## Target Architecture Layers

### 1. Domain Layer (`internal/domain/`)
- **Entities**: Core business objects (User, Portfolio, Transaction, Holding)
- **Interfaces**: Repository and gateway interfaces for external services
- **Value Objects**: Currency, TransactionType, etc.
- **Business Rules**: Domain-specific validation and logic

### 2. Use Case Layer (`internal/usecase/`)
- **Application Logic**: Orchestrate domain entities and external services
- **Use Case Interfaces**: Define what the application can do
- **DTOs**: Input/Output data structures for use cases

### 3. Infrastructure Layer (`internal/infrastructure/`)
- **gRPC Clients**: Implementations of domain gateways
- **Mappers**: Convert between protobuf and domain models

### 4. Presentation Layer (`graph/`)
- **Resolvers**: Thin layer that calls use cases
- **GraphQL Models**: Generated by gqlgen
- **Mappers**: Convert between GraphQL models and domain entities

## Implementation Steps

### Phase 1: Domain Layer
1. Create domain entities in `internal/domain/entities/`
2. Create domain interfaces in `internal/domain/gateway/`
3. Create value objects in `internal/domain/valueobject/`

### Phase 2: Use Case Layer
1. Create use case interfaces in `internal/usecase/`
2. Implement user use cases
3. Implement portfolio use cases
4. Implement transaction use cases

### Phase 3: Infrastructure Layer
1. Create gRPC gateway implementations in `internal/infrastructure/grpc/`
2. Create mappers in `internal/infrastructure/mapper/`
3. Wire up dependency injection

### Phase 4: Presentation Layer
1. Create presentation mappers in `graph/mapper/`
2. Refactor resolvers to use use cases
3. Remove direct gRPC client dependencies from resolvers

### Phase 5: Dependency Injection
1. Create container in `internal/container/`
2. Update main.go to use container
3. Wire all dependencies properly

## Benefits
- **Testability**: Each layer can be tested independently
- **Maintainability**: Clear separation of concerns
- **Flexibility**: Easy to swap implementations (e.g., REST instead of gRPC)
- **Domain Focus**: Business logic isolated from infrastructure concerns
